# 기능 게이트(LIVE / SHADOW / OFF) 정책

arm과 arm 안의 기능(예: TTL 규칙, 진입 필터)은 세 상태 중 하나다. 상태는 사람이 바꾸고, 레지스트리 JSON(`feature-flags.example.json` 형식)에 적으며, `scripts/feature_status.py`는 읽기만 한다.

## 상태 의미

| 상태 | 주문을 내는가 | 판단을 기록하는가 | 요구 조건 |
|---|---|---|---|
| LIVE | 낸다 | 낸다 | `evidence` 필수: 변경 기록 경로, 통과한 격리 스위트 결과, SHADOW 기간 측정치. 없으면 `feature_status.py`가 경고. |
| SHADOW | 내지 않는다 | "LIVE였다면 냈을 주문"을 로그·원장 관측 행으로 남긴다 | `expires` 필수. 측정 지표와 측정 기간은 변경 기록 2·3항에 미리 적는다. |
| OFF | 내지 않는다 | 남기지 않는다 | 끈 이유와 시각을 `notes`에. 승인된 14개 활성 arm을 OFF로 돌리는 것도 변경 승인 대상이다(AGENTS.md 23행). |

SHADOW는 "코드가 배포되어 있지만 주문 경로에서는 비활성"을 뜻한다. 코드가 소스에만 있고 런타임에 없는 것은 SHADOW가 아니라 "미배포"다. prism-insight가 겪은 "코드가 있다 ≠ 운영 중이다" 괴리를 피하려고 이 둘을 구분한다.

## 규칙

1. **자동 승격 금지.** SHADOW→LIVE는 사람이 변경 기록에 승인자·승인 시각(6항)을 적고 레지스트리를 고친 뒤, 정상 배포 창에서 배포해야 성립한다. 스크립트·야간 잡·LLM이 상태를 바꾸지 않는다.
2. **만료 시 OFF.** `expires`가 지난 SHADOW는 그 시점부터 OFF로 간주한다. 코드가 자동으로 끄지 못하더라도 레지스트리와 보고는 OFF로 적고, 다음 정상 창에서 코드도 OFF로 맞춘다. 연장하려면 새 만료일과 사유를 기록한다(연장도 변경이다).
3. **LIVE에는 만료가 없어도 되지만 증거는 있어야 한다.** 증거 없는 LIVE는 "왜 켜져 있는지 아무도 모르는" 상태이므로 경고 대상이다.
4. **한 줄에 한 게이트.** 같은 `name`이 두 줄이면 어느 쪽이 진실인지 알 수 없으므로 경고한다.
5. **게이트 이름 규약.** arm 전체는 원장 arm ID(`EXP_D`, `S5_steady_uptrend_vwap`), arm 안의 기능은 `<arm>/<기능>`(`EXP_D/auction_window_ttl`). 여러 arm에 걸치면 `scope`에 arm 목록을 적는다.
6. **LLM은 게이트 뒤에 들어가지 않는다.** 어떤 상태에서도 주문 판단에 LLM 호출을 넣는 게이트를 만들지 않는다.

## 누가 바꿀 수 있나

| 전환 | 누가 | 조건 |
|---|---|---|
| (없음)→SHADOW | 변경 작성자(Codex/Claude가 제안, 사용자가 승인) | 6항목 변경 기록, 격리 스위트 통과, 만료일 |
| SHADOW→LIVE | 사용자만 | SHADOW 측정치가 기록 2항의 기대와 맞는지 확인, 기록 6항에 승인 시각, 정상 창 배포 |
| LIVE→OFF, SHADOW→OFF | 사용자(긴급 시 운영자) | 사유·시각 기록. 긴급 OFF는 장중에도 "운영 설정 변경"이므로 AGENTS.md 17행과 충돌한다 — 봇의 자체 halt 경로를 쓰고 코드 변경은 창을 기다린다. |
| OFF→SHADOW/LIVE | 사용자만 | 새 변경 기록(이전 기록 재사용 금지) |

## 레지스트리 위치

실제 레지스트리는 봇 소스 트리 밖에 둔다(소스 manifest 해시 검증을 깨지 않기 위해). 권장: `reports/<날짜>/feature-flags.json` 또는 변경 기록 옆. `python3 scripts/feature_status.py --registry <경로>`로 읽는다.
