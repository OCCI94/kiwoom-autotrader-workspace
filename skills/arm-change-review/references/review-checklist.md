# arm 변경 검토 체크리스트

각 항목은 "확인함 / 해당 없음 / 미확인"으로 적는다. "미확인"이 하나라도 있으면 배포 창을 요청하지 않는다.

## A. 분류와 범위

- [ ] 결함 수정 vs 경제적 변경을 정했다. 판단 근거: 문서·설계가 말하는 동작과 코드 동작의 차이(결함) / 기대 손익 분포를 바꾸는 규칙 변경(경제적).
- [ ] 경제적 변경이면 §0 단계에서는 원칙적으로 보류하고, 1단계 가설 사전등록 대상으로 넘겼다.
- [ ] 변경이 건드리는 arm 목록과, 건드리지 않아야 하는 arm 목록을 적었다(예: C·GDR은 기존 TTL 유지).
- [ ] 승인된 `paper_experiment_v1`·14개 활성 arm을 되돌리거나 끄는 효과가 없는지 확인했다.

## B. 정합성 (프롬프트 ≠ 코드 ≠ 서버 괴리 차단)

- [ ] **문서 ↔ 코드**: `docs/PAPER_EXPERIMENT.md`, `UNFILLED_BUY_TTL.md`, `docs/S5_STEADY_UPTREND_VWAP.md` 같은 계약 문서의 숫자·시각·조건이 소스 상수와 같다.
- [ ] **지시문/프롬프트 ↔ 코드**: `*_INSTRUCTIONS.txt`, Telegram 안내문, 설정 설명 문자열이 코드 동작과 같은 숫자를 말한다. 프롬프트에만 있고 코드 강제가 없는 규칙은 없다(있으면 코드로 옮기거나 프롬프트에서 뺀다).
- [ ] **설정 기본값 ↔ 핫 정책**: `config/settings.py` 기본값, `config/paper_hot_policy.py` 허용 키, 프로필 파일 값이 서로 모순되지 않는다.
- [ ] **소스 ↔ 런타임**: 런타임 복사본(`~/Library/Application Support/KiwoomAutotrader/runtime/`)과 소스의 변경 파일 해시를 비교해, "검토한 소스"와 "지금 돌고 있는 것"의 차이를 안다. 런타임은 읽기만 한다.
- [ ] 같은 상수가 여러 파일에 흩어져 있으면 하나로 모았거나, 값 일치를 단언하는 테스트를 추가했다(prism-insight의 프롬프트 해시 테스트 패턴: 날짜·사유를 적은 정합 테스트).
- [ ] 줄 번호는 검토 시점 mtime과 함께 적었다(Codex가 동시에 편집한다).

## C. 테스트

- [ ] 변경 파일의 focused 테스트가 통과했다(검토 단계용).
- [ ] 배포 대상의 정확한 소스 manifest로 **전체 APP 격리 스위트**가 통과했다(네트워크·키체인·launchctl 차단, 격리 HOME; `work/isolated_app_tests.py`). 결과 파일·manifest를 배포 당일 `reports/<날짜>/`에 남겼다.
- [ ] 스위트 통과 후 소스가 바뀌지 않았다(manifest 해시 재확인). 바뀌었거나 날짜가 넘어갔으면 다시 돌린다.
- [ ] 시각 의존 로직은 KST 고정 시각으로 테스트했다(15:20, 15:29, 15:30, 15:31, 08:59, 09:00 경계).
- [ ] 휴장일·주말 경계를 "공식 달력 증거"로 테스트했다(임의 평일 계산 금지).

## D. 배포 도구 리허설 (2026-11-03 교훈)

- [ ] 배포 도구를 수리 시간대에 런타임 **복사본**을 상대로 dry-run 했다. 창 안에서 도구를 고치지 않는다.
- [ ] 도구의 "변경 없음" 검사가 금융 행(`intents`, `order_decisions`, `orders`, `fills`)만 열 단위로 비교하고, 수신기가 정상적으로 append하는 관측 행(`execution_observations`, `broker_observations`, `strategy_holding_observations`, `profit_observations` 등)은 허용하는지 확인했다. 파일 전체 해시 비교는 수신기를 멈추기 직전까지의 정상 기록을 "변경"으로 오판한다. 테이블명은 `execution_log.py`의 CREATE TABLE로 다시 확인한다.
- [ ] 도구가 실패했을 때 수신기를 원래 상태로 되돌리는 경로(재시작·state.json 확인)가 있다.

## E. 백업과 롤백

- [ ] 배포 직전 runtime·설정·원장 백업 경로와 SHA-256을 보고에 적었다.
- [ ] 롤백은 코드·설정만 되돌린다. 원장은 새 경제 이벤트가 생기면 과거 백업으로 덮지 않는다.
- [ ] 롤백도 배포 창·승인·claim이 필요함을 기록 4항에 적었다.

## F. 창과 승인

- [ ] `python3 scripts/deploy_window_check.py --kind normal --holidays <공식 휴장일 파일>`이 0으로 끝났다(또는 사용자 발급 예외 토큰이 있고 `--kind exception`이 0).
- [ ] 사용자의 **배포** 승인을 받았다(수리·재시작 승인과 별개).
- [ ] 이번 주 claim 잔량(화·목 각 1회, 주 2회; 실패·미확정 포함)을 사람이 세어 적었다.
- [ ] 장전 창이면 당일 공식 예정 세션 증거가 신선하다.

## G. 배포 후

- [ ] 실제 `state.json`에서 다음 5개 값을 그대로 인용했다: `pid`, `status`, `paper_experiment.enabled`, `active_arms`(14개인지), `halted`.
- [ ] 수신기 외 작업자(LaunchAgent 다른 label)가 바뀌었다면 별도 승인 범위 안인지 확인했다.
- [ ] 변경 기록에 배포 시각·manifest 해시·state.json 인용을 추가하고, 레지스트리 상태(SHADOW 등)를 사람이 갱신했다.
- [ ] 첫 거래일 마감 후 기록 2항의 지표를 한 번 집계해 기대와 다르면 즉시 보고했다.
