구현된 gdcrs 자동매수 요구사항 기록 (보관용)

이 파일은 이전 후속 구현 지시문을 구현된 기능의 요구사항·검증 기준으로 보관한 것입니다. 현재 버전은 start gdcrs로 등록 종목의 골든크로스 자동매수 감시를 켤 수 있습니다. 실제 서비스의 활성 상태는 실행 설정을 확인하세요. 유지보수 시 아래 계약을 보존하고 현재 소스와 테스트를 함께 확인하세요.

구현 위치: kiwoom_autotrader/trading/golden_cross.py의 GoldenCrossMonitor. 명령은 kiwoom_autotrader/telegram/commands/crosses.py, 검증은 tests/test_golden_cross.py, tests/test_golden_budget_guard.py, tests/test_cross_commands.py와 listener 통합 테스트를 참고하세요.

프로젝트 루트 AGENTS.md를 먼저 읽고 기존 기능과 설정을 보존하세요. TR 근거는 제공된 키움 REST API 문서.xlsx 및 /tr_docs/{TR명}.md입니다. 1분봉은 ka10080(/tr_docs/ka10080.md), 현재가는 ka10001(/tr_docs/ka10001.md), 매수는 kt10000(/tr_docs/kt10000.md) 명세에서 확인하세요. 파일에 없는 필드·동작을 추정하지 마세요.

명령과 저장 설정
- gdcrs intv {단기} {장기}: 각각 1~60 정수이며 공용 gdcrs_short_period, gdcrs_long_period를 저장합니다. 동일하거나 역순인 설정은 보존될 수 있으므로 실행 시작과 매 주문 직전에 1 ≤ 단기 < 장기 ≤ 60을 확인하세요.
- gdcrs add {종목코드} {예산}: gdcrs_stocks의 {code: 6자리 문자열, budget: 양의 정수 원화}를 관리합니다. 실제 명령 파서의 추가·삭제·조회 문법을 재사용하세요.
- start gdcrs / stop gdcrs: 시작은 gdcrs_enabled=true, 중지는 false를 영속 저장합니다. 단기<장기를 확인하고, 저장에 성공한 시작에만 CrossReplies.started_gdcrs=true를 반환합니다. 빈 목록에서도 활성화하여 추후 등록을 기다리며, 시작·등록 명령 자체로 즉시 매수하지 않습니다. 중지 시 ddcrs 상태와 목록·예산을 보존합니다.
- ddcrs_enabled 및 현재 ddcrs 자동매도 동작과 충돌하지 않게 통합하세요. 로그인 토큰·투자 구분은 현재 BrokerSession의 메모리 상태만 사용하고 키체인을 다시 읽거나 자동 로그인하지 마세요.

매수 기준과 주문
- KRX 당일 정규장에 종료된 1분봉 종가의 단순이동평균(SMA)을 사용하세요. ka10080 cntr_tm은 봉 시작 시각이므로 현재 진행 중인 봉을 제외하세요. 부호 있는 cur_prc의 절댓값을 가격으로 사용하세요.
- 장 시작·종료는 공용 market_start_time, market_end_time 설정을 사용하며 KRX 정규장 범위와 일치하는지 확인하세요. 활성화된 동안 장 종료 후에는 기다리고 다음 평일 장 시작에 관측을 다시 시작합니다. 대기 중 활성화 설정을 임의로 끄지 않고, stop gdcrs는 장중·장외 모두 false로 저장합니다. 거래일이 바뀌면 최초 관측을 다시 기준으로 삼으세요.
- 직전 관측 종료봉에서 단기 SMA ≤ 장기 SMA이고 새 종료봉에서 단기 SMA > 장기 SMA일 때만 골든크로스입니다. 시작·재시작·설정/로그인 변경 시 최초 관측은 기준만 저장하며 과거 신호를 실행하지 마세요.
- 봉 시간·종목·필요 이력·중복·공백·정규장·현재 날짜·최신성·관측 간 연속성과 겹치는 과거 봉의 수정 여부를 검증하세요. 자료가 불완전하면 주문하지 마세요.
- 등록 예산은 기존 buy {code} max {budget} 파서와 처리기를 재사용하세요. 수량=floor(예산/조회가)를 유지하고 수수료를 제외한 매수 원금을 제한합니다. 현재가가 공통 KRX 가격격자에 맞지 않으면 ka10004의 최근 실제 표시호가 중 현재가 이하 최고 가격을 지정가로 사용합니다. 가격을 추측하거나 올리지 않고, 낮아진 지정가 때문에 수량을 늘리지 않습니다. 조회가/실제 지정가 구분, 호가 검증 실패 시 무주문, 미체결 가능성, 수수료 별도, 1주 미만 무주문을 유지하세요.
- 주문 직전에 활성화 상태·설정·현재 BrokerSession의 mode/token/만료와 예산·현재가를 다시 검증하세요. 처리 도중 stop/reset 또는 로그인/투자구분 변경이 발생하면 제출하지 마세요.
- mode/symbol/종료봉 단위의 내구성 있는 주문 시도 기록을 주문보다 먼저 확정하세요. 실패·시간초과·응답 불명확·알림 실패에도 기록을 유지하여 같은 신호를 자동 재전송하지 마세요. 예약 매수·수동 주문·ddcrs와 동시에 실행되지 않도록 메인 명령 루프에서 직렬 처리하세요.
- 주문 결과가 불명확하면 OrderReplies.uncertain을 확인해 gdcrs_enabled=false로 영속 저장하고 엔진을 멈추세요. 사용자에게 주문내역 확인 후 명시적으로 start gdcrs할 것을 알리세요. 저장 실패 시 메모리 중지를 유지하고 실패를 알려야 합니다. 일반 로그인·설정 변경이 이 중지를 해제해서는 안 됩니다.
- 모든 HTTP 요청은 utils/http_queue.py의 queued_open을 통과시키고 자동 재시도를 추가하지 마세요. 데이터 조회와 주문 한도를 지키고 루프 한 번에 전체 등록종목을 무제한 순회하지 마세요.
- api.minute_chart.fetch_minute_chart의 ka10080 제한기는 같은 프로세스의 두 감시·모든 종목·세션·모의/실전·연속조회 페이지 사이에 최소 1.05초 간격을 적용합니다. 이 제한과 프로세스 간 공용 HTTP 전송 상한을 모두 보존하세요.

검증과 완료 기준
- 실제 API, Telegram, 키체인, 실전/모의 주문 호출 없이 주입한 가짜 응답으로 테스트하세요.
- 경계 교차/동일선, 현재봉 제외, 부족·오래된·중복·누락·수정 봉, 주말·장외·당일성, 시작/중지/재시작/설정변경, 로그인·모드·토큰변경, 예산 부족, 내구 기록 실패, 동일 신호 재시작 재생방지, 모호한 주문 결과의 무재시도를 검증하세요.
- 명세에 휴장일 API가 없으므로 휴장일 캘린더 유무를 명시하고 최신 당일 종료봉이 없으면 중단하세요. 주문 접수와 체결을 구분하고 사용자 메시지에 키·토큰·원격 원문을 출력하지 마세요.
- 구현한 파일·설정·검증 결과와 제한을 보고하세요. 사용자가 별도로 허용하기 전에는 실행 중 서비스를 재시작하거나 실거래 검증을 하지 마세요.

현재 공통 기반 재사용
- 자동매수 처리기는 trading.order_context.automated_orders(execution_tracker, "gdcrs") 문맥에서 호출하여 기존 주문 의도·접수·체결 원장과 일일결산에 연결하세요.
- WebSocket을 도입하면 realtime.get_websocket_engine(session)의 공용 엔진만 사용하세요. 별도 소켓이나 수신 루프를 생성하지 마세요. 초기 REST 방식은 유지할 수 있습니다.
