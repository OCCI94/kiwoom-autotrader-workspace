# 종료일 재대사: 장중 우선순위와 단계 관측

이 문서는 2026-11-04 사용자 보완 요청의 **소스 계약**이다. 운영 반영·현재 PID의 성능
개선 증명이 아니다. 원장·배정·설정·모의 실험 arm 및 금융 안전 한도를 변경하지 않는다.

## A. 장중에는 당일 tracker 작업만 처리

- 명시 보호창은 **09:00~09:05**, **15:20~15:30 KST**다. 보호창뿐 아니라 정규장
  전체에서 과거일 체결·비용 재조회, 결산 및 대형 파생 파일 재생성을 미룬다.
- 기본 과거일 보류 구간은 08:55~15:40이다. 검증된 공식 세션이 더 이르거나 늦으면
  보수적으로 범위를 넓히며, 확인되지 않은 시간을 공식 세션으로 표현하지 않는다.
  특별장이 16:30에 끝나면 과거일 작업 재개도 16:40 이후다. 이는 코드 배포 창과 별개다.
- 대기열에 이미 있던 과거일 작업과 과거일 매도 후 비용 갱신도 보류 대상이다. 당일
  작업과 섞여 있다는 이유로 역사 작업을 실행하지 않는다. 장외에 원래 대상에서 재검토한다.
- 당일 00 원문 저장, 현재 잔고·미체결과 전송 직전 안전 대사, 소유 보유분 청산은 유지한다.
  별도 이전 주문일 소멸 증명/보호 청산 경로를 역사 비용 재조회와 혼동하지 않는다.

## A와 함께 단계별 계측 및 상태 게시

첫 배포에서는 관측이 우선이다. 복사본 한 날짜의 파싱 벤치 1.6초는 실제 운영 루프가
220~286초 멈췄다는 관측을 설명하지 못한다. 새 로그를 실제로 수집하기 전에는 이 차이의
원인이 해결됐다고 보고하지 않는다.

- tracker 주기·논리 작업, 조회, SQLite snapshot/JSON 변환, fingerprint, JSONL 내보내기,
  accounting 및 요약의 시작/종료를 구분한다. 중첩 단계는 부모와 스레드를 연결한다.
  `tracker-diagnostics-YYYYMMDD.jsonl`의 파일 날짜는 기록일이며, 처리 대상의
  `work_day`·`mode`는 별도 필드다. 오늘 파일에 기록된 10/27 작업을 구분할 수 있어야 한다.
- 경과시간은 단조 시계로 계산한다. 처리 바이트는 원문 UTF-8, 파생 파일 쓰기 등 기준을
  함께 표시한다. 공급자 wire 바이트와 로컬 처리량을 합치지 않는다. 미계측은 `null`이다.
- 현재 RSS와 최고 RSS의 출처를 구분한다. 지원하지 않는 플랫폼의 값은 `null`이며,
  최고 RSS의 증가를 현재 메모리 잔량 감소로 해석하지 않는다.
- 진단에는 단계명·날짜·모드·건수·바이트·시간·메모리만 담는다. 원문 응답, 계좌번호,
  토큰, 메시지 본문은 기록하지 않는다. 파일 상한/기록 실패는 진단 상태에 드러낸다.
- listener는 tracker **전/후 및 주요 단계 경계**에 현재 상태를 게시한다. 게시 시각,
  monitor의 실제 마지막 완료 시각, tracker 단계 시작 시각은 각각 다른 필드다.
  게시 때문에 monitor tick 완료 시각을 앞으로 옮기지 않는다.
- recorder 상태를 새로 읽은 시각도 별도로 기록한다. 단계 게시만으로 오래된 `00 ready`를
  신선한 관측으로 만들지 않는다. 단계 callback 안에서는 recorder 잠금에 재진입하지 않는다.
- WS/회복 스레드의 기록은 listener 상태를 동시에 덮지 않는다. listener 소유 tracker
  스레드의 순서 있는 단계만 상태 게시 callback을 실행한다.
- 감시기 소스는 게시 지연, monitor 마지막 완료 경과, tracker 진행 단계 경과를 따로
  판정한다. 기존 120초 tick 경보는 유지하며, tracker 진행 중이라는 이유로 정상 처리하지 않는다.

`maximum_tick_duration_seconds=98.3`은 monitor 내부의 누적 최대다. 사용자는 이를
15:21:38~15:23:16의 monitor 작업으로 정정했다. 이후 실행되는 외부 tracker 시간과
직접 합치지 않는다. `tick_age`는 저장된 마지막 완료 정보의 나이지 함수 실행시간이 아니다.

## B. `limit_blocked`는 금융 정산 완료가 아님

비용 관측 누적 20,000행을 넘는 과거일은 JSON 전체 파싱보다 먼저 가벼운 범위 검사를
수행해 `limit_blocked`로 분리한다. 10/27은 기존 복사본부터 이미 이 조건에 해당한다.

- 해당 날짜의 자동 broker 재조회와 fingerprint 계산 자체를 중단한다. 이미 대기열에 있는
  작업에도 적용한다. 재기동은 비싼 전체 파싱 대신 같은 범위 검사를 다시 수행한다.
- 원본과 compact repeat의 **논리 관측 수**를 함께 센다. 저장 압축으로 제한 검사를 우회하지 않는다.
- 상태는 tracker 관리/진단에 한정한다. 미해결 금융행, 체결, 이력, 비용 `null`, 예약 상태를
  수정하지 않는다. `successful`/정산 완료/예약 해제의 증거로 쓰지 않는다.
- 원천이 append-only인데 같은 원인을 자동 재시도해도 상한은 해소되지 않는다. 재개하려면
  최신 완전 query를 먼저 검증하는 별도 소스 수리와 복사본 회귀가 필요하다.
- 일반 장기 대기는 여전히 `official_calendar_unavailable`과 공식 세션 수를 구분한다.
  N일이 지났다는 이유로 미검증 비용이나 실제 미체결을 종결하지 않는다.

### 검증된 취소 정산 공개의 예외

이미 검증·커밋된 취소 정산의 공개는 일반 과거 결산과 다르다. 전일 정산이 있다는 이유로
예약금 해제를 15:40까지 미루지 않는다. `_publish_settlement`는 정확한 주문·committed 증거
해시·경제 fingerprint가 일치하는 `_materialize_settlement_accounting` 전용 경로를 사용한다.
일반 `_materialize_accounting`과 history/summary의 장중 보류는 유지한다.

- 이 예외는 **A의 일반 과거일 보류만** 우회한다. B의 20,000행 제한은 우회하지 않는다.
- 쓰기 전후와 readback에서 증거를 검증하고, 세션·스트림·신선도 guard는 유지한다.
  recorder/session guard를 history lock 안에서 호출해 잠금 순서를 뒤집지 않는다.
- sidecar에 정확한 정산 증거가 공개되고 publication 레코드가 확정되기 전에는 예약 해제를
  인정하지 않는다. ACK만 있는 주문, 증거 충돌·만료·늦은 금융 변경은 계속 미확정이다.
- 새 prior-day API 조회나 정산 생성 스케줄러를 추가한 것은 아니다. 이미 committed된
  정산 공개 경로의 수리이며, 특정 운영 주문의 실제 해제는 별도 당일 증거로 확인한다.

## C. 메모리와 증분 처리

종료일 캐시가 날짜별 전체 raw snapshot과 파싱 트리를 붙잡지 않게 하고, 제한된 크기의
경제 메타데이터만 보관한다. 재조회 예정 시각 전에는 가벼운 원장 변경 표식이 같으면
비싼 fingerprint를 건너뛴다. 새 경제 변경을 단순 타임아웃으로 숨기지 않는다.

**영속 JSONL export cursor는 별도 후속 단계**다. 원장 정체성·스키마·행수·MAX(id),
기존 prefix/tail 해시와 파일 검증을 함께 구현·회귀하기 전까지 cursor를 신뢰하거나
기존 감사 이력을 삭제하지 않는다. 첫 날짜 접근의 기존 재작성 fallback은 유지한다.

## 검증과 배포 경계

- 전체 APP는 격리 HOME, 외부 네트워크·키체인·서비스 제어 차단 상태에서 검증한다.
  이번 준비의 추가 감사 가드는 운영 앱 파일/라이브 SQLite를 열지 못하게 한다.
- 이미 존재하는 배포 전 원장 복사본만 사용해 20,000행 초과 차단, 금융행 보존,
  보호창·일자 전환·잔여 작업·장시간 단계의 상태 게시를 검증한다.
- 오늘 소스 검증 결과는 내일 배포일의 정확한 manifest 검증을 대체하지 않는다.
- 내일 09:01 이전 런타임 변경은 금지한다. 다음 통상 검토 창은 **11/05 목 15:40 이후**다.
  공식 장외 확인, 당일 전체 APP/복사본 회귀, 백업 해시, 한 개의 승인된 claim 조건을 지킨다.
  이번 소스 준비는 claim을 만들거나 수신기·감시기·수집기를 재시작하지 않는다.
- WORK의 감시기 소스 보완과 실제 설치된 불변 작업자는 구분한다. 수신기 코드만 교체해서
  별도 설치본의 감시기 코드도 바뀌었다고 보고하지 않는다.

## 18:10 검토에서 추가한 배포 게이트

이번 수신기 배포 범위에 설치 감시기 `ce74d033` 교체를 포함하지 않는다. 감시기 새 reader는
별도 제안 항목이며, 별도 승인·검증 전에는 기존 불변 설치본을 유지한다.

구버전 listener는 새 진단 최상위 키 4개를 거부한다. 배포 도구의 롤백 경로는 정지·정비
상태와 동일 파일 세대를 검증하고, 원문을 비공개 백업한 후 아래 키만 제외하는 projection을
검증해야 한다. `next_offset`, 명령 카운터, PID/status 및 나머지 값은 보존한다.

`state_publication`, `tracker_diagnostics`, `telemetry_publish_error`, `recorder_snapshot_observed_at`

과거 state 파일 복원, 임의의 미지 키 삭제, 금융 DB/배정/설정 복원으로 대신하지 않는다.
정상 handoff 이후 또는 정비 마커가 사라진 불명확 구간에는 자동 stop/rollback하지 않는다.
사본 리허설과 old-reader 호환 증거가 배포 당일 보고에 없으면 배포하지 않는다.

지원 일반 배포 도구와 과거 incident 전용 V9를 구분한다. V9의 날짜·기존 실패·주문 바인딩을
새 정상 배포에 재사용하지 않는다. 일반 도구의 `deployed_paused`는 정상 handoff 완료가 아니다.
공식 종료 증명 형식, 미해결 주문 선행 조건과 정상 handoff 경로가 맞지 않으면 claim 전에 멈춘다.

배포 후 보고할 state 값은 `pid`, `status`, `automation_status.paper_experiment.enabled`,
`automation_status.paper_experiment.monitor.active_arms`, supervisor/monitor의 실제 `halted`다.
생산자가 `halted`를 기록하지 않았다면 `null/미계측`으로 보고하며 False를 만들지 않는다.
정비·failure/reason·종목별 격리는 별도 근거다.

첫 tracker 진단은 새 state의 `run_id`와 일치하는 JSONL begin/end를 연결한다. 기록일과
`work_day`, 모드, sequence/부모, 시간·바이트·RSS 기준 및 실패 여부를 보존한다. begin만으로
완료를 선언하지 않으며, end의 `failed=false`도 정산 성공·예약 해제의 증거로 쓰지 않는다.

취소 거부 응답 보존, 익일 소멸 증명, 15:30 취소 경합, 비용 모델, 라이브 원장 금지,
수집기 재시작의 기존 6건은 계속 유효하며 이번 계측 수리로 완료 처리하지 않는다.
